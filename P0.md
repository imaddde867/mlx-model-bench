## Verdicts

**Arm 3 is alive.** DESIGN's fear that plain `mlx_lm` cannot read the mixed-bit
OptiQ file is wrong at these pins. The per-module 8-bit overrides load cleanly
(`load_s` 4.6, correct answer). The design keeps all five arms; no collapse to 1/2/4.

**Arm 4 is dead on this machine.** `optiq serve` 0.7.3 answers `/v1/models`, then
every completion kills its generation thread:

```
RuntimeError: [metal::malloc] Attempting to allocate 11274289152 bytes which is
greater than the maximum allowed buffer size of 9534832640 bytes
```

This is not a permission, sandbox or OS issue. Metal refuses any **single**
allocation above 9,534,832,640 B = 8.88 GiB on this GPU (`applegpu_g16g`,
16 GiB RAM, 11.84 GiB recommended working set). Our own `mlx_lm` process
allocated 6.7 GB in the same shell, same user, same files, so nothing is being
blocked from reading memory or disk. The engine simply asks for one tensor bigger
than the device allows.

11,274,289,152 B = 10.5 GiB = exactly `42 layers × 2 × 8 heads × 256 × 32768 × 2 B`
— a workspace sized for 32768 positions. It is requested **when the model is
built**, not per request: a two-token prompt (`"Hi"`) asks for the same 10.5 GiB.
Reproduced six ways, always the same byte count:

- with and without `--kv-config`
- with the uniform 4-bit `rapid-mlx` checkpoint instead of OptiQ
- `--max-tokens 64`, `--prompt-cache-size 4096`, `--prefill-step-size 64`
- prompt `"Hi"` (2 tokens) vs a 34-token instruction

So it is not the KV quantizer, not the mixed-bit weights, not the request's
`max_tokens`, and not prompt length. `mlx_lm.server` on the same machine serves
the same file fine, so the transport is not the problem — optiq's gemma-4 model
build is. No CLI flag reaches it; it needs an optiq-side fix (a workspace that
streams, or one sized well under 8.88 GiB).

**Two OptiQ release defects**, both from copying the gemma-4-e4b-it allocation onto
a different model:

- `kv_config.json` has **24 entries (layer_idx 0–23)**; this model has **42
  layers**. Mixed-precision KV cannot cover it as shipped.
- The repo's own README says the per-layer bit allocation was "transferred" from
  `gemma-4-e4b-it-OptiQ-4bit` rather than measured — consistent with the above.

## Chat template controls

The template has **two** controls, not three. `enable_thinking` and
`conversational_mode` appear in `chat_template.jinja`; `thinking_token_budget`
does not — it is a serving-API parameter, not a template variable. AGENTS.md's
"three controls" line needs amending.

`enable_thinking` must be passed **explicitly**. The jinja defaults it to false,
but transformers injects `enable_thinking=True`, so omitting the kwarg silently
produces a `<|channel>thought` trace:

| kwargs | prompt tok | output |
|---|---|---|
| *(none)* | 34 | `<|channel>thought\nThinking Process: …` |
| `enable_thinking=false` | 27 | `391` |
| `enable_thinking=false, conversational_mode=true` | 54 | `391.` |
| `enable_thinking=true` | 34 | thinking, no EOS in 24 tok |

`conversational_mode=true` costs **+27 prompt tokens** of scaffolding. Primary
table must pin it and record the prompt length next to every number.

## Text / image / audio

The model card's conflict resolves in favour of the architecture, not of our arms:

- `rapid-mlx` MLX-4bit is **text-only** by construction — vision and audio tensors
  are excluded; the index contains only `language_model.*`.
- OptiQ ships `optiq_vision.safetensors` (0.96 GB) holding `vision_tower` (658
  tensors), `audio_tower` (751), `embed_vision`, `embed_audio`. Image *and* audio
  weights are present, despite the README promising only images.
- `mlx_lm` never touches that sidecar (arm 3 peaks at 6.53 GB = language tower
  only), so arms 1–3 are text-only in practice.
- `optiq serve` does enable the vision path ("vision serving enabled (image+text
  via optiq_vision sidecar)"), but arm 4 cannot complete a text request, so image
  input is **unverified** and audio is untested in every arm.

For the report: the model accepts text, image and audio in principle; on this
machine only text was demonstrated.

## Corrections to DESIGN.md

- Arm 1's checkpoint is **4.2 GB**, not 6.5 GB on disk (6.53 GB is the OptiQ
  language tower).
- Arm 4 must not be assumed runnable. Either optiq fixes the gemma-4 prefill
  buffer, or arm 4 becomes **OptiQ over `mlx_lm.server`** — same checkpoint, same
  HTTP shape as arm 2, and it is known to work here. That changes what arm 4
  measures (checkpoint over HTTP, not the optiq engine), so the report must say so
  and arms 4/5 stop being engine comparisons.

## Reproduce

```bash
uv venv .venv-mlxlm && uv pip install --python .venv-mlxlm/bin/python mlx-lm==0.32.2 mlx==0.32.4
.venv-mlxlm/bin/python p0_load.py models/rapid-mlx-4bit --template-kwargs '{"enable_thinking": false}'
.venv-mlxlm/bin/python p0_load.py models/optiq-4bit     --template-kwargs '{"enable_thinking": false}'
.venv-optiq/bin/optiq serve --model models/optiq-4bit --port 8097   # then any completion
```

Checkpoints live in `models/` (fetched by `curl`, not `hf cache`: hf restarted
mid-file twice and dropped ~2 GB of progress). `uv` resolved `transformers`
5.20.2 in `.venv-mlxlm` but 5.12.1 in `.venv-optiq`; the port must record which.
